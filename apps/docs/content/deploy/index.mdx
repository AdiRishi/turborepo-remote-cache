Because the server is a [Nitro](https://nitro.build) application, the same codebase builds for Cloudflare Workers, long-running Node.js/Bun/Deno processes, Vercel, Netlify, and AWS Lambda.

**Cloudflare Workers is the recommended default.** It's the only target that provisions artifact storage (R2), scheduled expiry, and a stats database (D1) automatically, and it's the target tested end-to-end against the real `turbo` CLI in CI.

## Feature matrix

| Platform                                 | Max upload payload       | Artifact storage                        | Scheduled expiry     | Stats database                              |
| ---------------------------------------- | ------------------------ | --------------------------------------- | -------------------- | ------------------------------------------- |
| [Cloudflare Workers](/deploy/cloudflare) | 100 MB (200 MB Business) | R2 (default), KV, S3, or custom adapter | Built-in cron        | D1 (auto-created on first deploy)           |
| [Node.js, Bun, and Deno](/deploy/node)   | Unlimited                | S3 or custom adapter                    | In-process scheduler | SQLite on Node.js & Deno; configure for Bun |
| [Vercel](/deploy/vercel)                 | 4.5 MB                   | S3 or custom adapter                    | Vercel Cron Jobs     | External hosted DB required                 |
| [Netlify](/deploy/netlify)               | ~4.5 MB                  | S3 or custom adapter                    | External scheduler   | External hosted DB required                 |
| [AWS Lambda](/deploy/aws-lambda)         | Under 6 MB (Base64)      | S3 or custom adapter                    | External scheduler   | External hosted DB required                 |

On platforms without built-in scheduling, trigger `POST /internal/delete-expired-objects` daily from an external cron (see [Run expiry from a scheduler](/retention#run-expiry-from-a-scheduler)). For database options on non-Cloudflare hosts, see [Stats database](/stats-database).

## Artifact size limits

If a build output exceeds your host's HTTP payload cap, `turbo` cannot upload it and that task will miss on every remote build. Modern monorepo outputs (Next.js `.next` builds, Rust/Wasm artifacts, large TypeScript bundles) routinely exceed 4.5 MB, so pick **Cloudflare Workers** or a **Node.js / Bun / Deno** process unless you know your outputs stay small.

- **Cloudflare Workers:** 100 MB on Free and Pro zones, 200 MB on Business (governed by your Cloudflare zone plan, not Workers plan). [Limits](https://developers.cloudflare.com/workers/platform/limits/#request-and-response-limits)
- **Node.js, Bun, and Deno:** No server-side cap (constrained only by any reverse proxy in front of the process).
- **Vercel / Netlify / AWS Lambda:** Hard serverless body limits of [4.5 MB on Vercel](https://vercel.com/docs/functions/limitations#request-body-size), [~4.5 MB on Netlify](https://docs.netlify.com/build/functions/configuration/) (6 MB buffered minus Base64 overhead), and [under 6 MB on Lambda](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html) (event envelope + Base64 overhead).
- **Storage limits:** Workers KV caps values at 25 MiB, and the S3 adapter buffers uploads in memory, so very large uploads require sufficient runtime RAM.

## Build from source

Every non-button deployment builds from your fork of the repository using Node.js 24+ and the pnpm version specified in `package.json`. Run `pnpm install` and build commands from the repository root, setting `NITRO_PRESET` for your target runtime:

| Platform           | `NITRO_PRESET`                |
| ------------------ | ----------------------------- |
| Cloudflare Workers | `cloudflare_module` (default) |
| Node.js            | `node_server`                 |
| Bun                | `bun`                         |
| Deno               | `deno_server`                 |
| Vercel             | `vercel` (auto-detected)      |
| Netlify            | `netlify` (auto-detected)     |
| AWS Lambda         | `aws_lambda`                  |

```sh
NITRO_PRESET=node_server pnpm build
```

:::warning[Check root `turbo.json` before building with `TURBO_TOKEN` set]
This repository's root `turbo.json` points at the maintainer's own remote cache. If `TURBO_TOKEN` is exported in your shell or CI environment during a build, `turbo` will send your token there. Remove the `remoteCache` block from the root `turbo.json`, or update it to your own server URL, before building.
:::

Other [Nitro presets](https://nitro.build/deploy) may also work, though only the Cloudflare Workers build runs full end-to-end `turbo` tests in CI.
